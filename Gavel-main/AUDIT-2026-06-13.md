## TIER 1: Security

### 🔴 C1, `/v1/payments` is mounted with NO authentication

`index.ts:178`:
```ts
app.use('/v1/payments', paymentsRouter); // ← no authenticateAnyToken
```
Every other protected router is mounted as `app.use('/v1/x', authenticateAnyToken, xRouter)`. The payments
router was not. Its handlers all assume auth ran and read `req.orgId!` (a non-null assertion), but
unauthenticated `req.orgId` is `undefined`. Consequences:

- **`POST /v1/payments/refund` (payments.ts:407)**, looks up the payment **by id only** and refunds it.
  There is no org check (`paymentData.orgId === req.orgId` is never compared). An anonymous caller can
  refund **any org's** captured payment and flip its status to `refunded`. (Money loss + fraud.)
- **`POST /v1/payments/record` (payments.ts:367)**, records a "captured" payment and marks the next EMI
  in `repayment_schedules` as **Paid**. Anonymous callers can mark loans paid. (Collections integrity.)
- **`POST /v1/payments/order` / `/link`**, create real Razorpay orders/links and write `payments` rows
  with `orgId: undefined`. (Cost/abuse + data pollution.)
- **`GET /v1/payments/:paymentId` (payments.ts:321)**, fetches any payment by id, no org check →
  cross-org data leak.
- Several handlers append to the immutable `audit_logs` collection with attacker-controlled / `undefined`
  `orgId` → audit pollution.

> **Note for the fix:** the router also exposes `POST /v1/payments/webhook`, which is (correctly)
> authenticated by Razorpay **signature**, not an API key. A blanket `authenticateAnyToken` on the whole
> router would break that webhook. The fix must auth the mutating routes (`/order`, `/link`, `/verify`,
> `/record`, `/refund`, `GET /`, `GET /:id`, `/analytics/summary`) while leaving `/webhook` signature-gated
>, i.e. apply the middleware per-route or split the webhook out (as `/v1/webhooks/razorpay` already is at
> `index.ts:155`). This is a product/topology decision, filed as a follow-up rather than patched blind.

**Maps to checklist:** TIER 1 #1 (unauthenticated route touching real data) and #4 (cross-org).

### 🔴 C2, `/v1/parse` is mounted with NO authentication

`index.ts:179`:
```ts
app.use('/v1/parse', pdfParserRouter); // ← no authenticateAnyToken, no enforceQuota
```
`POST /v1/parse/bank-statement` and `POST /v1/parse-and-analyze` accept a 10 MB PDF, extract text, and POST
it to the **NVIDIA LLM** (`routes/pdf-parser.ts:194`). Unauthenticated:

- **Cost-amplification DoS**, anyone can drive unbounded third-party LLM spend; there is no key, no
  `enforceQuota`, no org attribution. The only brake is the 100-req/min/IP `apiLimiter`, trivially bypassed
  with rotating IPs.
- **Unattributed PII processing**, arbitrary bank statements are parsed with no tenant on record.

If `/v1/parse` is intentionally public for the marketing-site demo, it must at minimum get its own strict,
per-IP quota and a documented "demo only" data path. Otherwise it must sit behind `authenticateAnyToken` +
`enforceQuota`. Filed as a follow-up (needs the product decision).

**Maps to checklist:** TIER 1 #1 and #7.

### ✅ #1 API-key validation (the rest), GOOD
- Keys are SHA-256 hashed (`middleware/auth.ts:18`), looked up by hash with `isActive == true`, and the org
  is bound from the key document, no plaintext keys stored.
- Key generation/deletion is behind `authenticateFirebaseToken` and org-scoped (`routes/apikeys.ts:13,60`;
  delete verifies `keyDoc.orgId === orgId`).
- All `/v1/*` routers **except** payments/parse (C1/C2) and the intentional `/v1/public` + custom-auth
  `/v1/borrower` are mounted behind `authenticateAnyToken`.

### ✅ #2 PAN data handling, GOOD (PR #2 still holds)
- Raw PAN is **never persisted**. The audit row and idempotency store only `panMasked = '******' + last4`
  (`routes/underwriting.ts:104-105,118`); the engine input object is not stored.
- PAN absent from the PDF binary: `tests/audit-pdf.test.ts:74` asserts
  `buf.includes(Buffer.from('ABCPK1234D')) === false` and **passes**. The PR #2 guarantee is intact.
- `/evaluate` also masks (`routes/evaluate.ts:172`). `usage_logs` records only the URL path, not the body.

### ✅ #3 Audit-log immutability, GOOD
- No route performs `UPDATE` or `DELETE` on `audit_logs`. Writes are either `.doc(audit_id).set(newRow)`
  (`routes/underwriting.ts:106`) or `.add()` appends (`payments.ts`, `evaluate.ts`, `disbursements.ts`).
- No admin backdoor to mutate a past decision was found.
- Firestore rules enforce WORM at the client edge: `audit_logs … allow write: if false`
  (`firestore.rules:63-66`); reads are org-scoped (`isOwner()`).
- ⚠️ See M3, `.set()` keyed by a 3-byte-entropy `audit_id` is a *theoretical* overwrite path; tighten it.

### ✅ #4 Org-scoping (underwriting paths), GOOD
- `GET /v1/underwriting/audit/:id/pdf` returns **404** for both "missing" and "wrong org"
  (`routes/underwriting.ts:194`), no existence leak. The route test for cross-org fetch passes.
- `routes/compliance.ts:60` correctly returns 403 when `audit_logs/:id.orgId !== req.orgId`.
- ⚠️ Org-scoping is **violated in payments**, see C1/H1.

### ✅ #5 Environment / secrets, GOOD
- No `sk_live` / cloud keys hardcoded, matches only display prefixes (`apikeys.ts:28`) and test fixtures.
- `.gitignore` covers `.env`, `.env.*`, `backend/.env`, `*.pem`, `*serviceAccountKey*`; no `.env` is tracked.
- `.env.example` ships empty placeholders only.
- `ANTHROPIC_API_KEY` is **not used** in the backend; LLM calls go to NVIDIA / Gemini, keyed from env
  (`process.env.NVIDIA_API_KEY`, `process.env.GEMINI_API_KEY`). Firebase creds load from
  `FIREBASE_SERVICE_ACCOUNT` / ADC (`config/firebase.ts`), none hardcoded.
- The committed `.git_disabled/config` remote URL contains **no** embedded credentials. (But see L3.)

### ✅ #6 Input validation / limits, GOOD (one gap: M4)
- `validateAnalyzeRequest` checks body shape, applicant name/PAN (regex `^[A-Z]{5}[0-9]{4}[A-Z]$`),
  non-empty `transactions[]`, and per-transaction `date`+`amount`. The engine defends numerically
  (`Number(t.amount) || 0`, balance filtered by `typeof === 'number'`), a malformed payload yields a 400
  or a clean E001, not a crash.
- Body size: `express.json({ limit: '10mb' })` + a `Content-Length > 10 MB → 413` guard (`index.ts:96`).
- PDF upload: `multer` `fileSize: 10 MB` + `application/pdf`-only filter (`pdf-parser.ts:18`).
- **Gap (M4):** no upper bound on `transactions.length`, see below.

### ✅ #7 Rate limiting / quota / replay, GOOD (gap: C2 has neither)
- Global `apiLimiter` 100/min/IP on `/v1`; `authLimiter` 20/15min on `/v1/apikeys`.
- `enforceQuota` is a Firestore **transaction** (`middleware/quota.ts:14`), atomic increment, no race; it
  runs on `/v1/underwriting/analyze` (after idempotency replay so retries aren't re-billed) and `/v1/evaluate`.
- Replay: the `Idempotency-Key` flow dedupes per-org and replays the stored result without a new charge
  (`routes/underwriting.ts:23-46,140-150`).
- **Gap:** `/v1/parse` has neither auth nor quota (C2). Quota only enforces a hard cap for `tier === 'startup'`
 non-startup tiers increment but are uncapped here (by design; billing happens elsewhere, confirm).

## TIER 2: Correctness

### ✅ #8 Determinism: GOOD (matches expectation)
`analyze()` is pure over `(input, policy)`. Across repeated runs the **decision, risk_score, credit_limit,
confidence, reasons and rule ledger are identical**; only `audit_id` (random per call, *as intended*) and
`processing_time_ms` vary. The engine test suite (`underwriting-engine.test.ts`, 19/19) and route suite
(8/8) confirm this. This exactly matches checklist #8: "same input → identical decision, unique audit_id."

### ✅ #9 Hard-reject precedence, GOOD (PR #1 still holds)
Decision order (`services/underwriting-engine.ts:309-318`): `hardReject → REJECT` is evaluated **before**
score bands, so a high-EMI applicant rejects regardless of a REVIEW-band score. The three hard-reject gates
in `pilot-acme.json`:

| Rule | Field | Condition (pass = good) | Fires REJECT when |
|------|-------|-------------------------|-------------------|
| R001 | `monthly_income` | `>= 20000` | income < ₹20,000 |
| R002 | `emi_ratio` | `<= 0.6` | EMI/income > 60% (the "high EMI" case) |
| R003 | `min_balance` | `>= 0` | any negative running balance |

Plus the data-sufficiency gate E001 (`months_of_data < 3 → REJECT`). All fire correctly. ⚠️ See M2 for the
fail-open edge.

### ✅ #10 Credit-limit formula, GOOD
`computeCreditLimit` (`underwriting-engine.ts:191`) with `pilot-acme.json`:
`limit = monthly_income × 7 × (risk_score / 100)`, rounded to nearest ₹10,000, clamped to
`[min_limit=0, max_limit=1,000,000]`; a REJECT forces `credit_limit = 0`. Caps are applied via
`Math.max(min, Math.min(max, limit))`, correct. Example: ₹50,000 income at score 80 → 50000×7×0.8 =
₹2,80,000 → rounds to ₹2,80,000, under the ₹10,00,000 cap. ✔

## Detailed findings (HIGH / MEDIUM / LOW)

### 🟠 H1: Payments lacks org-scoping on by-id operations
Independent of C1: even once auth is added, `GET /v1/payments/:paymentId` (`payments.ts:321`) and
`POST /v1/payments/refund` (`payments.ts:407`) resolve the payment **by document id alone** and never
compare its `orgId` to the caller's. Org A can read or refund Org B's payment by id. The fix that adds auth
**must also** add `if (paymentData.orgId !== req.orgId) return 404/403`. (The list/analytics endpoints
already filter by `orgId` correctly.)

### 🟠 H2: Backend test suite is red; CI gates on it
`npm run test` → **8 failed / 58**. `.github/workflows/ci.yml` `backend-test` runs `npm run test`, so `main`
is effectively unmergeable and the pre-pilot quality signal is broken. The failures are **test defects, not
engine bugs** (the underwriting engine/route/pdf suites are 33/33 green):
- 3× `hashApiKey` + 3× `sanitizeString` error with *"Cannot find package 'firebase-admin'"*, `unit.test.ts`
  uses `vi.resetModules()` + dynamic `import('../src/middleware/auth')`, which pulls real `firebase-admin`
  with no mock. Also `sanitizeString` is imported from `middleware/auth` but actually lives in the route
  files (`routes/agents.ts:12`, `routes/applications.ts:12`): the test targets a nonexistent export.
- `EMI Calculation` expects `88849` but the formula returns `8885` (expected value is 10× wrong).
- `Partner Service pipeline` expects `230000` but gets `280000` (wrong expected value).

Fix the tests (mock `firebase-admin`, import `sanitizeString` from its real module, correct the two expected
numbers) so CI is green before a pilot.

### 🟡 M1: Dead `audit-log.ts` route is an unscoped, in-memory loaded gun
`routes/audit-log.ts` is **imported** (`index.ts:40`) but **never mounted**, currently inert. If mounted,
its `GET /` returns **all tenants' logs** when the `tenantId` query param is omitted (it filters on a
*client-supplied* query param, never `req.orgId`), and it stores logs in a process-memory array (lost on
restart, the opposite of the durable WORM `audit_logs` collection). Delete it, or rewrite it to read the
Firestore `audit_logs` collection scoped to `req.orgId` (like `routes/compliance.ts` already does).

### 🟡 M2: Hard-reject gates fail-open on a missing signal
`underwriting-engine.ts:274-285`: a rule whose `field` resolves to `undefined`/`null` is marked `skipped`
and `continue`d **before** the action switch, so a `hard_reject` rule is silently *not enforced* if its
field is ever missing or renamed. All three current hard-reject fields are always derived, so this is not
exploitable today, but a future signal rename would silently disable a safety gate. Recommend: a skipped
`hard_reject` (or `review_flag`) should fail **closed** (force REVIEW/REJECT), not pass.

### 🟡 M3, `audit_id` entropy + `.set()` overwrite risk
`newAuditId = gavel_${ms}_${crypto.randomBytes(3)}`, only **24 bits** of randomness. The audit row is
written with `db.collection('audit_logs').doc(audit_id).set(...)` (`routes/underwriting.ts:106`), so a
same-millisecond collision would **silently overwrite** a prior immutable audit row, a direct hit to RBI
defensibility. Use ≥8–16 random bytes and/or `.create()` (which throws on an existing doc) instead of
`.set()`.

### 🟡 M4: Unbounded transaction array
`validateAnalyzeRequest` enforces `transactions.length >= 1` but no upper bound; the only ceiling is the
10 MB JSON body. A 10 MB transaction array runs several synchronous O(n) passes + a regex per transaction in
`deriveSignals`, blocking the event loop and starving other requests (single-request soft-DoS, within one
key's quota). Add a sane cap (e.g. reject `> 10,000` transactions with a 400).

### ⚪ L1: Idempotency replay ignores the request body
`idempotencyReplay` (`routes/underwriting.ts:23`) returns the stored result for a known key **without
checking the body matches**. Reusing a key with a different payload silently returns the old decision. Bind
the key to a hash of the request body and 409 on mismatch.

### ⚪ L2: Length-based token-type detection
`authenticateAnyToken` routes tokens `> 200` chars to the Firebase verifier, else to the API-key verifier
(`middleware/auth.ts:115`). Brittle: an unusually long API key would be sent to Firebase and 401. Low risk
(keys are server-generated to a fixed length), prefer a key prefix (e.g. `sk_…`) to disambiguate.

### ⚪ L3: Repo hygiene: committed git internals & error logs
A complete nested git store `.git_disabled/` (263 files, incl. a packed object store) plus `error.txt` and
`git_push_error.txt` are committed. The config has no creds and the error files have no secret patterns, but
`.git_disabled/objects/*` could contain historical blobs and it bloats the repo. Remove these and add them to
`.gitignore`.
